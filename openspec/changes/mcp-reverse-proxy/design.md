## Context

Мотивация — см. `proposal.md` → «Why». Здесь только то, что формирует техническое решение.

Ключевое ограничение — асимметрия эпох протокола. Спецификация `2026-07-28` вводит понятия **modern** (версия, capabilities и идентичность едут в `_meta` каждого запроса; сессий нет) и **legacy** (`2025-11-25` и ранее; сессия устанавливается хендшейком `initialize`). Наш фронт обязан быть modern, а практически все существующие stdio-бэкенды — legacy.

Из `2026-07-28` убрано ровно то, на чём держится legacy-мир: `initialize` / `notifications/initialized`, заголовок `Mcp-Session-Id`, server→client запросы (заменены паттерном MRTR), `resources/subscribe` / `unsubscribe` (заменены на `subscriptions/listen`), `ping`, `logging/setLevel`, возобновляемость SSE (`Last-Event-ID`). Deprecated отмечены Roots, Sampling и Logging.

Существенно для оценки объёма: сам перевод эпох реализован в `modelcontextprotocol/go-sdk`. Клиент SDK (`mcp/client.go`) выполняет спецификационную последовательность — пробует `server/discover`, при `UnsupportedProtocolVersionError` пересогласовывает версию, при любой другой ошибке откатывается на `initialize` + `notifications/initialized`. Поэтому предмет проекта — не трансляция протокола, а функции шлюза, которых в SDK нет: агрегация, конфигурация, политика, пул процессов, авторизация.

Состояние на входе: пустой репозиторий, кода нет.

## Goals / Non-Goals

**Goals:**

- Один HTTP-эндпоинт ревизии `2026-07-28`, за которым прозрачно работают N локальных stdio-серверов любой эпохи.
- Многопользовательский режим: два субъекта, обратившиеся к одному серверу, никогда не делят дочерний процесс.
- Конфигурация подключений из файла и из заголовка `x-mcp-config` по единым правилам слияния, с политикой поверх.
- Stateless-фронт: горизонтальное масштабирование не требует sticky-маршрутизации и общего хранилища состояния.

**Non-Goals:**

- Собственный авторизационный сервер. Прокси — только Resource Server; AS внешний.
- Проксирование HTTP MCP-серверов. В v1 бэкенды только stdio.
- Персистентность. Пул и кэши живут в памяти процесса.
- Elicitation / MRTR, Sampling, Roots, Logging, расширение Tasks — см. `proposal.md`.

## Decisions

### Слои обработки запроса

Разделение на четыре слоя — центральное решение; каждый следующий слой доверяет результату предыдущего и ничего не знает о его внутренностях.

```
  HTTP-запрос
      |
      v
 +--------------------------------------------------+
 |  1. AUTH     Bearer -> subject, scopes            |
 |              RFC 9728, проверка audience          |
 +--------------------------------------------------+
      |  subject, scopes
      v
 +--------------------------------------------------+
 |  2. POLICY   что этот subject вправе сделать      |
 |              заголовком x-mcp-config              |
 |              off | env-only | override-known |    |
 |              define-new                           |
 +--------------------------------------------------+
      |  разрешённая дельта конфига
      v
 +--------------------------------------------------+
 |  3. RESOLVE  base config <- merge <- header       |
 |              -> итоговый набор серверов + hash    |
 +--------------------------------------------------+
      |  resolved config
      v
 +--------------------------------------------------+
 |  4. POOL     (subject, hash) -> живой процесс     |
 |              spawn / reuse / restart              |
 +--------------------------------------------------+
      |
      v
   dual-era MCP client (go-sdk) -> stdio backend
```

**Почему auth и policy разделены.** Токен отвечает на вопрос «кто ты», а не «можно ли тебе запустить произвольный процесс». Заголовок `x-mcp-config` в режиме `define-new` передаёт `command`, `args` и `env` — это исполнение произвольного кода на хосте. Склеивание этих слоёв означало бы, что любой аутентифицированный субъект получает права на хост.

*Альтернатива:* один булев флаг «разрешать header-config». Отвергнута — не выражает промежуточные режимы, которые как раз безопасны и полезны (переопределить `env` у заранее описанного сервера).

### Режимы политики header-конфига

| Режим | Что разрешено заголовком |
|---|---|
| `off` | ничего; присланный заголовок отклоняется ошибкой, а не игнорируется молча |
| `env-only` | переопределять `env` у серверов из базового конфига |
| `override-known` | переопределять любые поля серверов из базового конфига |
| `define-new` | объявлять новые серверы с произвольными `command` / `args` |

Режим задаётся конфигурацией развёртывания и дополнительно ограничивается scope токена: повышающие режимы требуют отдельного scope (например `mcp:config:define`). Это даёт бесплатную интеграцию с OAuth-обработкой ошибок — недостающий scope возвращается как `403` с `WWW-Authenticate: error="insufficient_scope"` и списком требуемых scope, а клиент выполняет step-up авторизацию по спеке.

Дополнительные ограничения независимо от режима: allowlist исполняемых команд и denylist ключей `env`. Режим по умолчанию — `off`: небезопасная возможность включается осознанно, а не достаётся по умолчанию.

Молчаливое игнорирование заголовка в режиме `off` отвергнуто: субъект считал бы, что его конфигурация применена, и работал бы с чужим набором серверов, не зная об этом.

*Альтернатива:* передавать конфиг телом запроса, а не заголовком. Отвергнута для v1 как противоречащая исходному требованию, но ограничение реальное — размер заголовков обычно ограничен 8–16 КБ, и заголовки склонны попадать в логи обратных прокси. Отсюда требования: явный запрет логирования `x-mcp-config` и понятная ошибка при превышении лимита.

### Ключ пула процессов

Ключ — `(subject, hash(resolved server config))`, а не только хеш конфига.

`env` бэкенда, как правило, содержит персональные секреты (токены API). Если ключевать пул только конфигом, процесс, поднятый с секретами субъекта A, будет переиспользован для запроса субъекта B при совпадении конфигурации. Это тихая утечка, невидимая при тестировании с одним пользователем.

Следствие: число процессов растёт как «субъекты × серверы», поэтому обязательны idle-TTL, глобальный лимит и вытеснение по LRU. При неожиданном завершении процесс перезапускается; спека прямо разрешает потерять in-flight запросы, так как протокол stateless.

Дочерний процесс запускается в отдельной process group (`Setpgid` на POSIX; поддержка Windows через Job Objects вне v1), чтобы `SIGTERM` и `SIGKILL` доходили до всего дерева потомков, а не только до непосредственного ребёнка. Основной сигнал остановки — закрытие stdin, эскалация сигналами применяется, если процесс не завершился за отведённое время.

### Кэш-семантика результатов

Спека требует `ttlMs` и `cacheScope` на результатах `tools/list`, `prompts/list`, `resources/list`, `resources/templates/list` и `resources/read`.

Состав нашей поверхности зависит от субъекта и от `x-mcp-config`, поэтому `cacheScope` — всегда `"private"`. Значение `"public"` недопустимо ни при каких условиях: оно разрешило бы промежуточным кэшам отдать инструменты одного пользователя другому.

Порядок в `tools/list` детерминирован (сортировка по итоговому имени) — спека рекомендует это для кэширования на стороне клиента и попадания в prompt-кэш модели.

### Определение эпохи бэкенда

Используется штатная проба SDK, но с двумя добавками.

Откат на legacy в SDK срабатывает **по ошибке** от `server/discover`. Legacy-сервер, который на неизвестный метод молча не отвечает, подвесит подключение до дедлайна контекста — встроенного таймаута пробы нет. Поэтому: обязательный `probeTimeout` на контексте подключения и поле `era: auto | modern | legacy` в конфиге сервера, позволяющее пропустить пробу целиком.

Это не оптимизация «на потом»: пул ключуется по субъекту, значит холодные старты происходят часто, и полный таймаут пробы на каждом из них — заметная задержка первого запроса.

Определённая эпоха кэшируется на время жизни процесса бэкенда.

### Маскирование capabilities перед бэкендами

Прокси не анонсирует legacy-бэкендам capabilities `roots`, `sampling` и `elicitation`. Корректно написанный сервер тогда не станет отправлять соответствующие server→client запросы, и вопрос их трансляции не возникает. Запросы, пришедшие вопреки этому, отклоняются ошибкой.

Это решение — то, что удерживает фронт по-настоящему stateless: единственная конструкция, потребовавшая бы удерживать «замороженный» запрос между HTTP-раундтрипами, — MRTR, и она исключена из v1.

### Пространство имён

Имена инструментов, промптов и шаблонов ресурсов префиксуются идентификатором сервера из конфига. Разделитель фиксируется в спеке возможности; при коллизии итоговых имён запуск завершается ошибкой конфигурации, а не молчаливым выбором победителя.

URI ресурсов префиксовать тем же способом нельзя — у URI собственная структура со схемой. Поэтому исходный URI оборачивается: `mcp-proxy://<server-id>/<исходный URI в процентном кодировании>`, а `resources/read` разворачивает обёртку обратно. Схема обратима, не требует хранения таблицы соответствий и остаётся корректной при перезапуске шлюза.

*Альтернатива:* сохранять исходные URI и вести таблицу владения. Отвергнута — при совпадении URI у двух бэкендов различить их нечем, а таблица не переживает перезапуск.

### Фан-ин уведомлений

`subscriptions/listen` входит в первую поставку: это ядро ревизии, а не deprecated-возможность, и без него клиент не узнаёт об изменении состава инструментов иначе как опросом.

`subscriptions/listen` фронта — один долгоживущий поток. На modern-пути клиент SDK при подключении сам открывает `subscriptions/listen` к бэкенду под зарегистрированные `*ListChangedHandler`. Для legacy-бэкендов — а это подавляющее большинство — уведомления `listChanged` приходят по старому механизму. Фан-ин обязан принимать оба источника и приводить их к единому виду, проставляя `io.modelcontextprotocol/subscriptionId` фронтового потока.

### Поведение при недоступности отдельного бэкенда

Перечисляющие методы не отказывают целиком, если один бэкенд не отвечает: возвращаются элементы доступных, факт недоступности пишется в журнал, а `ttlMs` сокращается, чтобы клиент перепросил раньше обычного.

Отказывать целиком означало бы, что один сбойный бэкенд выводит из строя весь шлюз. Молча отдавать неполный список без сокращения `ttlMs` тоже плохо: клиент закэширует урезанный набор инструментов на полный срок и будет считать, что их не существует. Сокращённый срок жизни кэша — компромисс между этими крайностями.

Вызов инструмента недоступного бэкенда, в отличие от перечисления, возвращает явную ошибку: здесь тишина недопустима.

### Идентификатор субъекта

Субъект определяется парой `iss` + `sub` проверенного токена, а не одним `sub`. Значения `sub` уникальны только в пределах эмитента, а метаданные ресурса допускают несколько авторизационных серверов — при одном лишь `sub` два пользователя разных эмитентов с совпадающим идентификатором разделили бы дочерний процесс со всеми его секретами.

### Выбор языка

Go. Решающий фактор — статус SDK: `go-sdk` относится к Tier 1 (поддержка новой ревизии в день выхода) и уже содержит и modern-сервер, и dual-era клиент.

*Рассмотрены и отвергнуты:*

- **TypeScript** — SDK v2 сопоставим по возможностям, но пул с состоянием на `(subject × сервер)` плохо переживает масштабирование через `cluster`: пул либо дублируется по воркерам, либо выносится в отдельный сервис.
- **Java** — сильнее в OAuth (Spring Security) и в обходе деревьев процессов (`ProcessHandle.descendants()`), но SDK относится к Tier 2: стабильная линия 2.x реализует legacy-ревизию `2025-11-25`, а `2026-07-28` заявлена только в невыпущенной 3.x. Отсутствует ровно та половина, которая составляет смысл продукта, а обязательство Tier 2 — окно в шесть месяцев на каждую будущую ревизию.
- **Rust** — нет Tier-1 SDK.

## Risks / Trade-offs

- **`define-new` равносилен удалённому исполнению кода** → режим выключен по умолчанию, требует отдельного scope, ограничен allowlist команд; в документации помечен как доверенное окружение.
- **Секреты в `x-mcp-config` попадают в логи обратного прокси** → запрет логирования заголовка на своей стороне и явное предупреждение в документации по развёртыванию; заголовок не включается в сообщения об ошибках.
- **Исчерпание ресурсов хоста при росте «субъекты × серверы»** → глобальный лимит процессов, лимит на субъекта, idle-TTL, вытеснение по LRU, метрики размера пула.
- **Зависший `connect()` на legacy-бэкенде, молчащем на `server/discover`** → обязательный `probeTimeout`, возможность зафиксировать `era` в конфиге.
- **`go-sdk` молод, API может меняться** → зафиксировать версию в `go.mod`, изолировать вызовы SDK за внутренними интерфейсами, чтобы смена версии не расходилась по всей кодовой базе.
- **Legacy-бэкенд игнорирует немаскированные capabilities и всё равно шлёт server→client запрос** → отвечать ошибкой и логировать; это осознанная деградация, а не сбой прокси.
- **Утечка дочерних процессов при аварийном завершении прокси** → эскалация `SIGTERM` → `SIGKILL` по группе процессов, закрытие stdin как основной сигнал остановки.

## Migration Plan

Проект новый, миграции с существующей системы нет. Развёртывание: бинарник + конфиг-файл + доступ к внешнему OAuth AS. Откат — возврат предыдущего бинарника; состояние не персистится, поэтому обратных преобразований не требуется.
